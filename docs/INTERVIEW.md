# 安心保 Agent 项目 · 面试故事集

记录开发过程中可以在面试里讲的项目故事，重点是 Agent / RAG 相关的设计取舍与踩坑。
每个里程碑结束后更新；设计依据见 [SPEC.md](SPEC.md)（决策编号 D1–D30、原项目问题 P1–P10、风险 Q1–Q11）。

## 怎么用这份文档

每个故事按 STAR 写：背景（S）、要解决的问题（T）、做了什么与为什么这么取舍（A）、结果（R）。面试时先讲一句话结论，再按面试官的兴趣往下展开。

- **状态**：「设计」= 决策已做、代码未写；「已实现」= 代码已合入；「有数据」= 结果有真实测量（来自评测记录）。
- **诚实原则**：结果栏只写测到的数字，没测的写「待测」。被追问时说得清来源，比数字漂亮更重要。
- **随开发更新**：每个里程碑结束后，把踩过的坑、对比实验、改过的设计补进来；「待采集故事」一节列了每个里程碑要留意的素材。
- **证据**：尽量附上 commit、评测运行 ID 或 trace 链接，方便面试前回顾。

## 已有故事

### 故事 1：重构前先审计，在教学项目里找到 10 个问题

**一句话**：我没有直接照着教程抄，而是先把参考实现当作「待评审的代码」读一遍，列出 10 个问题，再针对性地设计。

- **S**：参考的保险顾问教学项目（FastAPI + LangGraph + Milvus）能跑通，但只实现了推荐一个分支。
- **T**：在从零重写前弄清楚「哪些地方不能照着做」。
- **A**：按模块读路由、工具、入库流水线和接口，发现的 Agent 相关问题最典型的是：
    - 检索工具的 `k` 和 `product_id` 完全由 LLM 填写，没有校验；
    - 条款 Markdown 交给 LLM 一次性改写，`max_tokens=10000`，长文会被截断，也不校验原文是否被改；
    - 异步图里调用同步 `invoke`，会阻塞事件循环；
    - 回答不返回条款出处；有费率表数据，却没有报价工具，用户问价格时只能靠 LLM "估"；
    - 用户身份直接信任 `x-user-id` 请求头。
- **R**：10 个问题（P1–P10）每个都在 spec 里有对应方案，成为后面几个故事的起点。
- **可能追问**：哪个问题最危险？→ 条款被 LLM 改写。保险条款一字之差就是赔与不赔，而且这类错误不会报错，最难发现。

### 故事 2：工具参数不交给 LLM 决定

**一句话**：LLM 只负责「想查什么」，「怎么查、查哪个产品」由代码根据对话状态决定。

- **S/T**：原项目让 LLM 填 `k` 和 `product_id`。LLM 可能编一个不存在的 ID，或把 `k` 填得很大导致上下文爆炸。
- **A**：`k` 由检索配置固定；产品只能从当前对话的候选集合里选；工具入参用 Pydantic 校验，出错时返回结构化错误让 LLM 组织话术，而不是抛异常。
- **R**：待测。计划在路由/工具评测中统计「工具参数非法率」。
- **可能追问**：这样会不会限制 Agent 的灵活性？→ 会，这是有意的取舍：在金融场景下，可控比灵活重要。

### 故事 3：选「路由 + 子图」，而不是单 ReAct 或 Supervisor

**一句话**：四个业务（条款问答、推荐、报价、理赔）各是一个子图，前面用一个路由节点分发。

- **对比的三个方案**：
    - 单 ReAct Agent 挂所有工具：写起来最快，但工具一多就难控制顺序（比如没问清年龄就报价），也难按业务分开评测。
    - Supervisor 多 Agent：表达力最强，但多一层 LLM 调度，延迟和成本都上升，调试也更难。
    - 路由 + 子图：每条业务的流程是确定的，可以单独测试和评测。
- **细节**：寒暄用正则拦截，不走 LLM；路由时带上「上一轮所在的工作流」，处理「那它等待期多久？」这类省略主语的追问。
- **R**：待测。路由评测集目标 ≥200 条（含多轮追问），报告准确率和混淆矩阵。
- **可能追问**：路由错了怎么办？→ 实现后补充（看混淆矩阵里哪两类最容易混）。

### 故事 4：报价不让 LLM 算数

**一句话**：保费由纯函数按费率表计算，LLM 只负责收集参数和解释结果。

- **S/T**：原项目有 10 份费率表却没有报价工具。让 LLM 报价，数字不可复现，也无法核对。
- **A**：
    - `quote(product, plan, params)` 不依赖 LLM；参数缺失时返回 `missing_params`，由 Agent 去追问。
    - 费率表 PDF 解析成结构化数据，脚本校验（单调性、完整性）后人工抽查，再入库。
    - 每次报价记下参数和费率版本，可以复现。
- **R**：待测。目标是费率表抽样点 100% 一致。
- **可能追问**：费率表格式不一致怎么办？→ 归成 6 种费率类型（固定保费、年龄段、每千元保额等），每种一个计算策略。解析的真实难点待 M5 补充。

### 故事 5：方案确认用 interrupt

**一句话**：Agent 生成方案后暂停，用户确认或修改后，图从断点继续执行并报价。

- **S/T**：推荐方案是写操作（会存库、会报价），不能让 LLM 自己决定「用户同意了」。
- **A**：用 LangGraph `interrupt` 暂停；前端收到 `plan_card` SSE 事件展示方案卡片；用户操作后调 `/chat/resume` 恢复。状态存在 Postgres checkpointer，服务重启也能接着走。
- **R**：待实现（M6）。
- **可能追问**：用户不确认而是发了新消息怎么办？→ M6 时要设计并记录。

### 故事 6：长期记忆要用户确认才写入

**一句话**：画像从对话里自动抽取，但只作为「建议」推给前端，用户点确认才写库。

- **S/T**：画像会被带到所有后续会话，还影响报价。一次误抽取（比如把「我妈 58 岁」记成用户本人 58 岁）会长期污染结果。
- **A**：每轮抽取增量 → SSE `profile_suggestion` → 用户确认 → `PUT /profile`。画像是结构化字段而不是自由文本，每个字段记录来源（chat / manual）。
- **取舍**：多一步确认会增加打扰。对保险这种强依赖个人信息、又涉及隐私的场景，可控和知情比无感更重要。
- **R**：待实现（M7）。

### 故事 7：换掉 Milvus，一个库解决一致性

**一句话**：用 PostgreSQL + pgvector 同时承担业务数据、向量和全文检索，父子块在一个事务里写入。

- **S/T**：原项目子块在 Milvus、父块在 PG，双写没有事务，中途失败会出现「子块指向不存在的父块」；部署还要多起 etcd、minio、milvus、attu 四个容器。
- **A**：单库事务写入；向量检索和 `tsvector` 全文检索两路召回，用 RRF 融合后再重排；中文分词放在应用层（jieba），不用自己编译数据库插件。网络调用（解析、向量化）全部放在事务外，事务内先锁文档行再删旧块、写新块，防止同一文档并发入库写出两份。
- **R**：部署从 5 个存储类容器减到 1 个；单事务写入已在 M2 实现，并有测试证明向量化失败时上一版块原样保留；检索质量对比待 M3 测。
- **可能追问**：数据量大了怎么办？→ 当前是 10 份条款、两千多个块，pgvector 绝对够用；到百万级向量、需要独立扩容时再考虑专用向量库。先说清条件，而不是说谁更好。

### 故事 8：评测集会"自己考自己"

**一句话**：用 LLM 按条款生成的问题，措辞和原文太像，检索指标会偏高；所以另写一组口语化难题，单独报告。

- **S/T**：需要 150+ 条条款问答和 200+ 条路由样本，全部手写不现实。
- **A**：LLM 按父块生成问题 + 人工审核；另手写 ≥30 条口语化、跨章节的难题，指标分开报告；端到端评测用 LLM-as-judge，再人工抽检 20%，报告两者一致率。
- **R**：待测。预期难题子集的召回明显低于生成集，这个差距本身就是个好故事。
- **可能追问**：LLM-as-judge 可信吗？→ 所以要报告它和人工判断的一致率，而不是直接拿来当真值。

### 故事 9：用规则重建条款结构，规则从真实解析结果里一条条补出来

**一句话**：不让 LLM 改写条款，而是用编号规则重建章节层级；第一版规则在真实数据上暴露了 8 类问题，逐个修复并加回归测试后，福有余条款的父块从 10 个恢复到 25 个，最长子块从 7754 字降到 1130 字。

- **S**：M2 入库，10 份条款经 MinerU 解析成 Markdown。MinerU 给的 `#` 级别不可靠，原项目的做法是让 LLM 整篇改写。
- **T**：在不改动条款原文的前提下，得到正确的章节路径（用于引用出处和父块上下文）。
- **A**：
    - 只做删行、拆行、接行、改标题标记，正文一个字不改；8 类编号（第X部分 / 第X条 / （一） / 一、 / （1） / 1. / 1.1 / 1.1.1）按首次出现顺序分配层级，中文和数字两套编号体系都适用。
    - 第一版规则是用 pypdf 文本设计的。拿到 MinerU 真实输出后逐份检查，发现：漏了「一、」编号；MinerU 会把整句话标成标题；同级的（一）（二）被错误嵌套；PDF 换行把列表项截成「带编号的半句话」被误判成标题；三栏目录挤成一行；双栏排版把「标题 + 正文」合成一行（星辰守护一份就有 93 处）；附表疾病定义变成长达 7754 字的表格。
    - 对应规则：带层级的标题栈、数字编号前缀一致性（9.4 只能挂在 9. 下）、接断行、删目录块、拆双栏行、长表格按行拆并保留表头。每条规则一个回归测试，测试用例直接取自真实输出。
    - 每一步的删除/合并/拆分次数写进文档统计，在管理后台展示，新条款结构异常一眼可见。
- **R**：10 份条款全部入库，共 974 个父块、1423 个子块；福有余父块 10 → 25；最长子块 7754 → 1130 字。检索效果待 M3 评测。
- **已知局限**：双栏排版的左栏标题会被截断（「1.2 合同成立与生」），只影响引用展示的标题。
- **可能追问**：规则怎么保证对新条款也有效？→ 不能保证，所以把结构统计做成可观测的（超大章节、超长标题、修正父级次数），新条款入库后先看统计。为什么不用 LLM？→ 长文会被截断、无法保证不改原文、每次重跑都有成本，而规则可解释、可测试、零成本。
- **证据**：commit `c8c9edf`；`backend/app/rag/structure.py`、`backend/tests/test_rag_structure.py`。

## 高频追问与回答要点

Agent 岗位面试常见的追问。要点都指向上面的故事，实现后补充具体数字。

| 追问 | 回答要点 | 故事 |
| --- | --- | --- |
| 你怎么减少幻觉？ | 分三层：数字不让 LLM 生成；工具参数由代码约束；回答强制带引用，检索不到就拒答 | 2、4、8 |
| 为什么用 LangGraph？ | 需要显式状态、条件路由、interrupt 和持久化 checkpointer；纯 Chain 做不了中断恢复 | 3、5 |
