# 安心保 Agent 项目 · 面试故事集

记录开发过程中可以在面试里讲的项目故事，重点是 Agent / RAG 相关的设计取舍与踩坑。
每个里程碑结束后更新；设计依据见 [SPEC.md](SPEC.md)（决策编号 D1–D39、原项目问题 P1–P10、风险 Q1–Q17）。

## 怎么用这份文档

每个故事按 STAR 写：背景（S）、要解决的问题（T）、做了什么与为什么这么取舍（A）、结果（R）。面试时先讲一句话结论，再按面试官的兴趣往下展开。

- **状态**：「设计」= 决策已做、代码未写；「已实现」= 代码已合入；「有数据」= 结果有真实测量（来自评测记录）。
- **诚实原则**：结果栏只写测到的数字，没测的写「待测」。被追问时说得清来源，比数字漂亮更重要。
- **随开发更新**：每个里程碑结束后，把踩过的坑、对比实验、改过的设计补进来；「待采集故事」一节列了每个里程碑要留意的素材。
- **证据**：尽量附上 commit、评测运行 ID 或 trace 链接，方便面试前回顾。

## 已有故事

### 故事 1：重构前先审计，在教学项目里找到 10 个问题

**一句话**：我没有直接照着教程抄，而是先把参考实现当作「待评审的代码」读一遍，列出 10 个问题，再针对性地设计。

- **S**：参考的保险顾问教学项目（FastAPI + LangGraph + Milvus）能跑通，但只实现了推荐一个分支。
- **T**：在从零重写前弄清楚「哪些地方不能照着做」。
- **A**：按模块读路由、工具、入库流水线和接口，发现的 Agent 相关问题最典型的是：
    - 检索工具的 `k` 和 `product_id` 完全由 LLM 填写，没有校验；
    - 条款 Markdown 交给 LLM 一次性改写，`max_tokens=10000`，长文会被截断，也不校验原文是否被改；
    - 异步图里调用同步 `invoke`，会阻塞事件循环；
    - 回答不返回条款出处；有费率表数据，却没有报价工具，用户问价格时只能靠 LLM "估"；
    - 用户身份直接信任 `x-user-id` 请求头。
- **R**：10 个问题（P1–P10）每个都在 spec 里有对应方案，成为后面几个故事的起点。
- **可能追问**：哪个问题最危险？→ 条款被 LLM 改写。保险条款一字之差就是赔与不赔，而且这类错误不会报错，最难发现。

### 故事 2：工具参数不交给 LLM 决定

**一句话**：LLM 只负责「想查什么」，「怎么查、查哪个产品」由代码根据对话状态决定。

- **S/T**：原项目让 LLM 填 `k` 和 `product_id`。LLM 可能编一个不存在的 ID，或把 `k` 填得很大导致上下文爆炸。
- **A**：`k` 由检索配置固定；产品只能从当前对话的候选集合里选；工具入参用 Pydantic 校验，出错时返回结构化错误让 LLM 组织话术，而不是抛异常。
- **M4 实现**：
    - 路由模型只输出 `{intent, product_ids}`，代码把 id 和产品目录求交集：编造的 id、字符串里的非数字、布尔值都丢掉；只剩编造的 id 时转为追问「哪款产品」，而不是去检索。
    - 查哪几份条款由代码根据产品决定（产品 → `clause_file` → 已入库的文档），检索参数在配置里固定，LLM 碰不到。
    - 引用由代码从回答里的 `[n]` 解析，只保留本轮真实检索到的编号；模型写出 `[10]`（把「第十条」当成编号）这种越界编号会被丢弃，前端也不会把它渲染成可点的出处。
    - 测试：用脚本化的假 LLM 让路由返回编造的 id，断言状态里只剩真实 id（这条测试先在去掉校验的代码上跑过一次，确认会失败）。
- **R**：已实现并有单测；「工具参数非法率」的统计留给 M8 路由评测。
- **可能追问**：这样会不会限制 Agent 的灵活性？→ 会，这是有意的取舍：在金融场景下，可控比灵活重要。

### 故事 3：选「路由 + 子图」，而不是单 ReAct 或 Supervisor

**一句话**：四个业务（条款问答、推荐、报价、理赔）各是一个子图，前面用一个路由节点分发。

- **对比的三个方案**：
    - 单 ReAct Agent 挂所有工具：写起来最快，但工具一多就难控制顺序（比如没问清年龄就报价），也难按业务分开评测。
    - Supervisor 多 Agent：表达力最强，但多一层 LLM 调度，延迟和成本都上升，调试也更难。
    - 路由 + 子图：每条业务的流程是确定的，可以单独测试和评测。
- **细节**：寒暄用正则拦截，不走 LLM；路由时带上「上一轮所在的工作流」，处理「那它等待期多久？」这类省略主语的追问。
- **M4 实现**：条款问答一条线 `route → prepare → answer`，状态里记「上一轮业务」和「上一轮产品」。用户只说「等待期多久」时追问产品；下一句只回「众安尊享e生」时，路由沿用上一轮业务，补全指代后接着回答原来的问题。
- **踩到的坑**：开场白里写了「可以查询等待期、保障范围……」，用户接着问「等待期多久？」，路由模型判成了闲聊（它以为用户在接开场白的话）。修复是在提示词里把 chitchat 收窄为「不涉及任何具体保险内容」，并明确「问到条款内容即使没提产品也是 clause_qa」。
- **R**：多轮追问在真实模型上验证通过；路由准确率待 M8 评测（目标 ≥200 条，含多轮追问）。
- **可能追问**：路由错了怎么办？→ 解析失败兜底到唯一已实现的业务（最坏多问一句「哪款产品」）；分类错误看 M8 的混淆矩阵。

### 故事 4：报价不让 LLM 算数

**一句话**：保费由纯函数按费率表计算，LLM 只负责收集参数和解释结果。

- **S/T**：原项目有 10 份费率表却没有报价工具。让 LLM 报价，数字不可复现，也无法核对。
- **A**：
    - `quote(product, plan, params)` 不依赖 LLM；参数缺失时返回 `missing_params`，由 Agent 去追问。
    - 费率表 PDF 解析成结构化数据，脚本校验（单调性、完整性）后人工抽查，再入库。
    - 每次报价记下参数和费率版本，可以复现。
- **R**：待测。目标是费率表抽样点 100% 一致。
- **可能追问**：费率表格式不一致怎么办？→ 归成 6 种费率类型（固定保费、年龄段、每千元保额等），每种一个计算策略。解析的真实难点待 M5 补充。

### 故事 5：方案确认用 interrupt

**一句话**：Agent 生成方案后暂停，用户确认或修改后，图从断点继续执行并报价。

- **S/T**：推荐方案是写操作（会存库、会报价），不能让 LLM 自己决定「用户同意了」。
- **A**：用 LangGraph `interrupt` 暂停；前端收到 `plan_card` SSE 事件展示方案卡片；用户操作后调 `/chat/resume` 恢复。状态存在 Postgres checkpointer，服务重启也能接着走。
- **R**：待实现（M6）。
- **可能追问**：用户不确认而是发了新消息怎么办？→ M6 时要设计并记录。

### 故事 6：长期记忆要用户确认才写入

**一句话**：画像从对话里自动抽取，但只作为「建议」推给前端，用户点确认才写库。

- **S/T**：画像会被带到所有后续会话，还影响报价。一次误抽取（比如把「我妈 58 岁」记成用户本人 58 岁）会长期污染结果。
- **A**：每轮抽取增量 → SSE `profile_suggestion` → 用户确认 → `PUT /profile`。画像是结构化字段而不是自由文本，每个字段记录来源（chat / manual）。
- **取舍**：多一步确认会增加打扰。对保险这种强依赖个人信息、又涉及隐私的场景，可控和知情比无感更重要。
- **R**：待实现（M7）。

### 故事 7：换掉 Milvus，一个库解决一致性

**一句话**：用 PostgreSQL + pgvector 同时承担业务数据、向量和全文检索，父子块在一个事务里写入。

- **S/T**：原项目子块在 Milvus、父块在 PG，双写没有事务，中途失败会出现「子块指向不存在的父块」；部署还要多起 etcd、minio、milvus、attu 四个容器。
- **A**：单库事务写入；向量检索和 `tsvector` 全文检索两路召回，用 RRF 融合后再重排；中文分词放在应用层（jieba），不用自己编译数据库插件。网络调用（解析、向量化）全部放在事务外，事务内先锁文档行再删旧块、写新块，防止同一文档并发入库写出两份。
- **R**：部署从 5 个存储类容器减到 1 个；单事务写入已在 M2 实现，并有测试证明向量化失败时上一版块原样保留。M3 在同一个库里做完了向量 + 全文 + 重排三路对照（结果见故事 10），召回阶段（两路 SQL + 取详情）P50 约 70–90 ms，延迟大头在外部接口：向量化 P50 约 490 ms、重排 P50 约 1.3–1.7 s。
- **踩到的坑**：pgvector 的 HNSW 是「先找近邻再过滤」，默认只找 40 个近邻；按条款过滤后可能只剩几条。用 pgvector 0.8 的 `hnsw.iterative_scan` 解决（过滤后不够会继续往下找），并有测试覆盖条款过滤。
- **可能追问**：数据量大了怎么办？→ 当前是 10 份条款、两千多个块，pgvector 绝对够用；到百万级向量、需要独立扩容时再考虑专用向量库。先说清条件，而不是说谁更好。

### 故事 8：评测集会"自己考自己"

**一句话**：用 LLM 按条款生成的问题，措辞和原文太像，检索指标会偏高；所以另写一组口语化难题，单独报告。

- **S/T**：需要 150+ 条条款问答和 200+ 条路由样本，全部手写不现实。
- **A**：LLM 按父块生成问题 + 人工审核；另手写 ≥30 条口语化、跨章节的难题，指标分开报告；端到端评测用 LLM-as-judge，再人工抽检 20%，报告两者一致率。
- **R**（M3，eval_runs #1–#6）：
    - 生成：10 份条款按章节顺序等距抽 178 个章节，qwen-plus 出题并给出原文依据，脚本校验依据逐字出现在章节里（丢 5 题）；人工审核再删 7 题（目录残留、问公司名之类的元问题），剩 166 题。另手写 34 道口语化 / 同义改写 / 跨章节难题。
    - **量化了「措辞像原文」**：问题与标准章节的最长公共子串，生成集中位数 6 字，难题集 2 字。
    - **差距确实很大**：纯向量 R@5 生成集 0.982、难题集 0.794；MRR 0.891 vs 0.592。只看生成集会以为检索已经「做完了」（混合 + 重排 R@5 = 1.000）。
    - 审核时顺带发现了 2 类结构问题（长病种标题没识别、一份条款的目录没删干净），评测集也是数据质量的检查工具。
- **可能追问**：LLM-as-judge 可信吗？→ 所以要报告它和人工判断的一致率，而不是直接拿来当真值。
- **可能追问**：34 题的难题集够吗？→ 不够做精细调参（一题就是 3 个百分点），所以只用它看方向、不用它挑最优参数；调参结论要在两个集上方向一致才采用（见故事 10）。
- **证据**：`data/eval/`、`backend/app/eval/`、报告 `eval/reports/retrieval-document-20261121-185832.md`。

### 故事 9：用规则重建条款结构，规则从真实解析结果里一条条补出来

**一句话**：不让 LLM 改写条款，而是用编号规则重建章节层级；第一版规则在真实数据上暴露了 8 类问题，逐个修复并加回归测试后，福有余条款的父块从 10 个恢复到 25 个，最长子块从 7754 字降到 1130 字。

- **S**：M2 入库，10 份条款经 MinerU 解析成 Markdown。MinerU 给的 `#` 级别不可靠，原项目的做法是让 LLM 整篇改写。
- **T**：在不改动条款原文的前提下，得到正确的章节路径（用于引用出处和父块上下文）。
- **A**：
    - 只做删行、拆行、接行、改标题标记，正文一个字不改；8 类编号（第X部分 / 第X条 / （一） / 一、 / （1） / 1. / 1.1 / 1.1.1）按首次出现顺序分配层级，中文和数字两套编号体系都适用。
    - 第一版规则是用 pypdf 文本设计的。拿到 MinerU 真实输出后逐份检查，发现：漏了「一、」编号；MinerU 会把整句话标成标题；同级的（一）（二）被错误嵌套；PDF 换行把列表项截成「带编号的半句话」被误判成标题；三栏目录挤成一行；双栏排版把「标题 + 正文」合成一行（星辰守护一份就有 93 处）；附表疾病定义变成长达 7754 字的表格。
    - 对应规则：带层级的标题栈、数字编号前缀一致性（9.4 只能挂在 9. 下）、接断行、删目录块、拆双栏行、长表格按行拆并保留表头。每条规则一个回归测试，测试用例直接取自真实输出。
    - 每一步的删除/合并/拆分次数写进文档统计，在管理后台展示，新条款结构异常一眼可见。
- **R**：10 份条款全部入库，共 974 个父块、1423 个子块；福有余父块 10 → 25；最长子块 7754 → 1130 字。检索效果待 M3 评测。
- **代码审查又抓到的问题**：删目录块的规则只比较「第 1 章编号是否出现第二次」，而 `1.` 的正则会匹配到 `1.1`——目录项早被逐行删掉时，它把真正的第 1 章标题和一段定义正文（「‘您’指投保人」）一起删了，3 份条款受影响，测试和统计都没发现。修复：编号后不能紧跟数字，且两次出现的**标题文字必须相同**；目录块内的完整句子保留。教训：**删除型规则要专门验证「删掉了什么」**，现在改规则后会在全部真实条款上列出被删的行逐条核对。同一轮还发现「标题含逗号就当正文」误伤了 2 个真实标题（改为看括号是否配对）、「第 1章」这种带空格的阿拉伯数字章号没识别。
- **已知局限**：双栏排版的左栏标题会被截断（「1.2 合同成立与生」），只影响引用展示的标题。
- **可能追问**：规则怎么保证对新条款也有效？→ 不能保证，所以把结构统计做成可观测的（超大章节、超长标题、修正父级次数），新条款入库后先看统计。为什么不用 LLM？→ 长文会被截断、无法保证不改原文、每次重跑都有成本，而规则可解释、可测试、零成本。
- **证据**：commit `c8c9edf`；`backend/app/rag/structure.py`、`backend/tests/test_rag_structure.py`。

### 故事 10：原以为混合检索一定更好，难题集上它反而更差

**一句话**：加上全文召回后，口语化难题的 R@5 从 0.794 掉到 0.676，因为口语里的「住院」「钱」「报」在条款里到处都是；真正起作用的是重排，而且换一个重排模型（gte-rerank-v2 → qwen3-rerank）难题集 R@5 就从 0.79 到 0.91——调参不如换对组件，而这只有难题集看得出来。

- **S**：M3 做混合检索（pgvector 向量 + PostgreSQL 全文，RRF 融合，再用 gte-rerank-v2 重排），在生成集 166 题 + 手写难题 34 题上做三组对照。
- **T**：用数据决定线上用哪种配置，而不是默认「混合 + 重排」就一定最好。
- **A**：
    - 先把全文召回做对：PostgreSQL 的 `ts_rank` 不看词的稀有程度，每个子块又都带条款名前缀，几乎所有块同分；改成按 BM25 的 IDF 给命中词加权（SQL 里逐词求和），并忽略出现在一半以上子块里的词。
    - 三组对照的结果：

        | 评测集 | 配置 | R@1 | R@5 | MRR@10 | P50 |
        |---|---|---|---|---|---|
        | 生成集 | 纯向量 / 混合 / 混合+重排 | .819 / .843 / .970 | .982 / .994 / 1.000 | .891 / .907 / .984 | 569 / 580 / 2310 ms |
        | 难题集 | 纯向量 / 混合 / 混合+重排 | .471 / .235 / .500 | .794 / .676 / .794 | .592 / .439 / .619 | 547 / 548 / 2047 ms |

    - **原以为……结果发现……**：原以为混合检索至少不会比纯向量差。结果在难题集上 R@1 从 0.47 掉到 0.24。看错题：「生病住院，自己要先掏多少钱保险才开始报？」，全文一路把十几个「住院医疗费用」章节排在前面，因为它们字面上命中「住院」「费用」「保险」，而真正的答案在「免赔额」一节，问题里一个字都没出现。RRF 给两路同样的权重，噪声一路就把好结果挤下去了。
    - 试了降低全文权重（1.0 → 0.5 → 0.3）：不重排时难题集 MRR 0.44 → 0.47 → 0.51，仍不如纯向量的 0.59；**加上重排后，三个权重的结果几乎一样**（两个集上差异都不超过 1 题：重排对前 30 个候选重新打分，候选集合基本没变）。所以线上默认保持「混合 + 重排」、权重不动，而没有为了 34 道题去调一个最优权重。
    - 最后对比了两个重排模型（其他不变）：

        | 难题集 | R@1 | R@5 | MRR | 总 P50 |
        |---|---|---|---|---|
        | gte-rerank-v2 | .500 | .794 | .619 | 2047 ms |
        | qwen3-rerank | .735 | .912 | .818 | 2391 ms |

      生成集上两者几乎一样（R@1 .970 vs .964），**只有难题集能区分它们**——这也是故事 8 里坚持单独做难题集的价值。原以为 qwen3-rerank 更快（单次试调 0.5 秒 vs 1.6 秒），批量跑下来 P50 相近，单次测量不可信。
    - 剩下 3 道没进前 5 的难题都是口语和条款术语之间的鸿沟：「之前就有的病」↔既往症、「刚买完就查出来」↔等待期、「突发心梗走了」↔疾病/猝死免责。这是查询改写要解决的问题，留给 M4（路由后先把问题改写成条款用语）。
- **R**：线上默认「混合 + 重排（qwen3-rerank）」：相对纯向量，生成集 R@1 0.82 → 0.96，难题集 R@5 0.79 → 0.91、MRR 0.59 → 0.82；代价是 P50 延迟多约 1.7 秒（重排接口）。所有数字来自 eval_runs #1–#22，管理后台「评测记录」页可查。
- **可能追问**：34 题上的差距可信吗？→ R@5 多对 4 题、R@1 多对 8 题，方向和幅度都远超 1 题的噪声，且生成集上没有变差，所以采纳；但全文权重那种 ≤1 题的差异就不采纳。延迟代价 M4 看端到端再评估（可减少候选数）。
- **可能追问**：为什么不直接用 Elasticsearch 的 BM25？→ 数据量只有 1400 个子块，在 PG 里用 IDF 加权已经够用，而且能和向量检索在一条 SQL 链路里按条款过滤；全文一路的问题不在打分公式，在于口语词本身没有区分度。
- **证据**：`backend/app/rag/retriever.py`；`eval/README.md`；eval_runs #1–#22。

### 故事 11：查询改写的提升，是我把评测集写进了提示词

**一句话**：给检索加了「口语→条款术语」的查询改写，难题集 R@5 从 0.912 涨到 0.971；后来发现提示词里的示例就是照着难题集错题写的。去掉这些示例重测，改写在两个集上都比不改写差，于是线上不换术语，只用改写补全指代。

- **S**：M4 做条款问答。M3 留下的问题（Q14）是口语和术语的鸿沟：「自己先掏多少钱」对应免赔额，难题集错题大多是这类。
- **T**：试查询改写能不能补上这个鸿沟，用评测说话。
- **A**：
    - 评测脚本加了 `--rewrite`，用线上同一个改写函数；又加了 `--keep-original`（改写结果和原问题一起召回）。
    - 第一版结果很好看：难题集 R@5 0.912 → 0.971、MRR 0.818 → 0.878（#45）。
    - **原以为……结果发现……**：原以为是改写起作用了。整理结果时回头看提示词，里面的「口语→术语」示例：自己先掏的钱→免赔额、买之前就有的病→既往症、刚买完多久能赔→等待期、取钱→减保、用保单借钱→保单贷款……全是我分析难题集错题时看到的。这是数据泄漏：评测集的答案写进了模型输入。
    - 去掉这些示例，只描述原则重测：难题集 R@5 0.941、MRR 0.785，生成集 MRR 0.980 → 0.962，都不如不改写（#46/#47 对 #21/#22）。
    - 看具体例子，改写把「哪些人住院时可以报销陪护人员的加床费？」变成了「住院医疗费用 加床费 陪护人员 保险责任 责任免除」：丢掉了和条款原文一致的措辞，又加了噪声关键词。
    - 决策：线上改写只补全指代（「那生孩子呢」→「生孩子住院能报吗」），不换术语；第一句没有上文就不改写，还省一次 LLM 调用；改写结果和原问题一起召回。
- **R**：评测集上的独立问题，线上检索等于基线（混合 + qwen3-rerank：难题集 R@5 0.912、MRR 0.818）；口语鸿沟仍是已知局限（Q14）。所有数字来自 eval_runs #21–#49，见 `eval/README.md`。
- **教训**：评测集只能用来评估，看过的失败案例不能回流到提示词或规则里；需要调参时要留出单独的开发集。这条已写进 CLAUDE.md。
- **可能追问**：那 M3 里根据难题集选 qwen3-rerank 算不算泄漏？→ 那是在两个现成模型之间选一个，没有把题目内容写进系统；而且生成集上两者持平，结论不依赖难题集的具体题目。但严格来说也该有开发集，M8 扩充评测集时会拆出来。
- **证据**：`backend/app/agent/prompts.py` 的 REWRITE；`eval/README.md`「查询改写」一节；eval_runs #39–#49。
