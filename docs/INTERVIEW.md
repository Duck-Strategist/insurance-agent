# 安心保 Agent 项目 · 面试故事集

记录开发过程中可以在面试里讲的项目故事，重点是 Agent / RAG 相关的设计取舍与踩坑。
每个里程碑结束后更新；设计依据见 [SPEC.md](SPEC.md)（决策编号 D1–D61、原项目问题 P1–P10、风险 Q1–Q25）。

## 怎么用这份文档

每个故事按 STAR 写：背景（S）、要解决的问题（T）、做了什么与为什么这么取舍（A）、结果（R）。面试时先讲一句话结论，再按面试官的兴趣往下展开。

- **状态**：「设计」= 决策已做、代码未写；「已实现」= 代码已合入；「有数据」= 结果有真实测量（来自评测记录）。
- **诚实原则**：结果栏只写测到的数字，没测的写「待测」。被追问时说得清来源，比数字漂亮更重要。
- **随开发更新**：每个里程碑结束后，把踩过的坑、对比实验、改过的设计补进来；「待采集故事」一节列了每个里程碑要留意的素材。
- **证据**：尽量附上 commit、评测运行 ID 或 trace 链接，方便面试前回顾。

## 已有故事

### 故事 1：重构前先审计，在教学项目里找到 10 个问题

**一句话**：我没有直接照着教程抄，而是先把参考实现当作「待评审的代码」读一遍，列出 10 个问题，再针对性地设计。

- **S**：参考的保险顾问教学项目（FastAPI + LangGraph + Milvus）能跑通，但只实现了推荐一个分支。
- **T**：在从零重写前弄清楚「哪些地方不能照着做」。
- **A**：按模块读路由、工具、入库流水线和接口，发现的 Agent 相关问题最典型的是：
    - 检索工具的 `k` 和 `product_id` 完全由 LLM 填写，没有校验；
    - 条款 Markdown 交给 LLM 一次性改写，`max_tokens=10000`，长文会被截断，也不校验原文是否被改；
    - 异步图里调用同步 `invoke`，会阻塞事件循环；
    - 回答不返回条款出处；有费率表数据，却没有报价工具，用户问价格时只能靠 LLM "估"；
    - 用户身份直接信任 `x-user-id` 请求头。
- **R**：10 个问题（P1–P10）每个都在 spec 里有对应方案，成为后面几个故事的起点。
- **可能追问**：哪个问题最危险？→ 条款被 LLM 改写。保险条款一字之差就是赔与不赔，而且这类错误不会报错，最难发现。

### 故事 2：工具参数不交给 LLM 决定

**一句话**：LLM 只负责「想查什么」，「怎么查、查哪个产品」由代码根据对话状态决定。

- **S/T**：原项目让 LLM 填 `k` 和 `product_id`。LLM 可能编一个不存在的 ID，或把 `k` 填得很大导致上下文爆炸。
- **A**：`k` 由检索配置固定；产品只能从当前对话的候选集合里选；工具入参用 Pydantic 校验，出错时返回结构化错误让 LLM 组织话术，而不是抛异常。
- **M4 实现**：
    - 路由模型只输出 `{intent, product_ids}`，代码把 id 和产品目录求交集：编造的 id、字符串里的非数字、布尔值都丢掉；只剩编造的 id 时转为追问「哪款产品」，而不是去检索。
    - 查哪几份条款由代码根据产品决定（产品 → `clause_file` → 已入库的文档），检索参数在配置里固定，LLM 碰不到。
    - 引用由代码从回答里的 `[n]` 解析，只保留本轮真实检索到的编号；模型写出 `[10]`（把「第十条」当成编号）这种越界编号会被丢弃，前端也不会把它渲染成可点的出处。
    - 测试：用脚本化的假 LLM 让路由返回编造的 id，断言状态里只剩真实 id（这条测试先在去掉校验的代码上跑过一次，确认会失败）。
- **R**：已实现并有单测；「工具参数非法率」的统计留给 M8 路由评测。
- **可能追问**：这样会不会限制 Agent 的灵活性？→ 会，这是有意的取舍：在金融场景下，可控比灵活重要。

### 故事 3：选「路由 + 子图」，而不是单 ReAct 或 Supervisor

**一句话**：四个业务（条款问答、推荐、报价、理赔）各是一个子图，前面用一个路由节点分发。

- **对比的三个方案**：
    - 单 ReAct Agent 挂所有工具：写起来最快，但工具一多就难控制顺序（比如没问清年龄就报价），也难按业务分开评测。
    - Supervisor 多 Agent：表达力最强，但多一层 LLM 调度，延迟和成本都上升，调试也更难。
    - 路由 + 子图：每条业务的流程是确定的，可以单独测试和评测。
- **细节**：寒暄用正则拦截，不走 LLM；路由时带上「上一轮所在的工作流」，处理「那它等待期多久？」这类省略主语的追问。
- **M4 实现**：条款问答一条线 `route → prepare → answer`，状态里记「上一轮业务」和「上一轮产品」。用户只说「等待期多久」时追问产品；下一句只回「众安尊享e生」时，路由沿用上一轮业务，补全指代后接着回答原来的问题。
- **踩到的坑**：开场白里写了「可以查询等待期、保障范围……」，用户接着问「等待期多久？」，路由模型判成了闲聊（它以为用户在接开场白的话）。修复是在提示词里把 chitchat 收窄为「不涉及任何具体保险内容」，并明确「问到条款内容即使没提产品也是 clause_qa」。
- **R**：多轮追问在真实模型上验证通过；M8 路由测试集 203 题（55 道多轮）准确率 0.956、多轮 0.964、产品识别 0.991（#143）。错题集中在条款问答 ↔ 理赔（「骑电动车摔了能报吗」没说是否已出险，本身有歧义）。
- **可能追问**：路由错了怎么办？→ 解析失败有兜底，不让整轮失败；分类错误看混淆矩阵——最常见的条款问答 ↔ 理赔互判，两条线都会检索条款，用户看到的差别是理赔多了材料清单和日期判断。

### 故事 4：报价不让 LLM 算数

**一句话**：保费由纯函数按费率表计算，每行明细带「费率表第几页、哪一格」；LLM 只负责收集参数和解释结果。费率表提取最大的坑是空白单元格让数字错列，靠「按单元格位置提取 + 业务规律校验」挡住。

- **S/T**：原项目有 10 份费率表却没有报价工具。让 LLM 报价，数字不可复现，也无法核对。M5 要把费率表变成可计算、可追溯、可复现的数据。
- **A**：
    - 引擎是纯函数：参数缺失返回 `missing_params`（Agent 去追问），不可投保返回原因和可选项（「65 周岁不能选5年交，可选：趸交」），不抛异常。
    - **原以为……结果发现……**：原以为费率表 PDF 都有文字层，按空格切文本就行。结果高龄行的空白格不在行尾：福有余 59 岁有 9 年交没有 10 年交，新华 61 岁起只剩男女两列趸交，按文本切数字会整体左移到别的列，而且「看起来」完全正常。改成按表格线取单元格，并且每个提取函数先核对表头文字再取值。
    - 列映射写错时结构校验看不出来，所以加了业务规律校验：交费期越长每千元保费对应的保额越高、同一列随年龄不增、无社保不低于有社保、计划档次递增。测试里故意对调两列，校验必须报错。
    - 原以为「表里有这一行就能投」。众安的表列到 105 岁，但注释写着 71 岁以上只适用于续保；门急诊加油包表列到 65 岁，首投却只到 55 岁。可投保年龄改由规则决定，不由表决定。
    - 抽查点的期望值不能来自提取脚本（否则是「自己考自己」，同故事 8）：渲染 PDF 页面图像，人工读出 60 个点写进单测，含 10 个应不可投保的空白格。
    - 费率 JSON 进仓库审 diff；入库整份存 JSONB，版本 = 文本哈希，旧版本保留，报价记录引用具体版本，费率表更新后旧报价仍能按当时的数据重算。
    - 第二批是 887 页（达尔文12号）和 180 页（医联有盟）的长表。pdfplumber 跑 887 页超过 10 分钟没跑完；pypdfium2 的整页文本又把一行拆成好几行。改成取每个字符的坐标自己拼行，结果小数点自成一行——它比数字矮，按字符中心分行就被分出去了，改按底边分行才对。
    - 达尔文12号的 96 个计划是 6 项可选责任的组合。发现编号是混合进制（1 + 48×身故 + 24×疾病关爱 + … + 多次给付 0/1/2），写成公式，提取时和 PDF 计划对照表逐行核对：71 行能完整读出，全部一致；剩下 25 行说明文字折行读不全，靠「加选一项责任保费必须更高」在 5 万个单元格上兜底，再用第 264 页的计划 48（就在读不全的 25 行里）独立验证。
    - 星相守的费率表分「有/无等待期」，原以为对应「个人版/转保版」两个产品。翻条款发现无等待期只适用于意外和续保，费率表里没有任何信息能区分转保版的价格——宁可不支持，也不猜。
- **R**：10 个产品、63,821 个单元格全部通过结构和业务校验；107 个人工抽查点 100% 一致（`tests/test_pricing_samples.py`）。达尔文12号的费率表 6 MB，解析一次约 0.4 秒，按版本 id 缓存后报价走内存。未覆盖的是星相守转保版（信息不足）和几个按保额计价、费率表没给保额范围的附加责任（spec Q18）。
- **可能追问**：
    - 为什么不让 LLM 读费率表？→ 一个数字错了没人发现；而且同样的输入要得到同样的报价，还要能指出依据在第几页。
    - 为什么不把每个单元格存成一行？→ 引擎每次都整产品读取，从不按单元格查；整份存反而让「引用版本」变简单（D41）。
- **证据**：`backend/app/pricing/`（extract、engine、tables）；`tests/test_pricing_engine.py` 的 `test_check_catches_swapped_pay_term_columns`；spec D41–D43。

### 故事 5：方案确认用 interrupt

**一句话**：Agent 生成方案后用 `interrupt` 停下等用户；按钮和直接打字都能恢复。打字时由模型判断是确认、调整还是问别的；问别的就让方案过期、把这句话交给路由——中断不会悬空，用户也不用先取消方案才能问问题。

- **S/T**：推荐方案是写操作（会存库、会报价），不能让 LLM 自己决定「用户同意了」，也不能让 LLM 编数字。
- **A**：
    - 分工：LLM 只抽取需求槽位（代码逐项校验：200 岁、负预算直接丢弃）和写几句说明；选产品、定保额是代码规则，保费全部来自 M5 的报价引擎（故事 4）。
    - 图：`collect → recommend → present → review`。**原以为** interrupt 可以和生成卡片放在一个节点里，**结果发现**恢复执行时被中断的节点会从头重跑——会重复落库、重复调用模型。于是 interrupt 单独放在 review 节点（D49）。
    - 用户不点按钮而是打字（D48）：`/chat` 发现会话停在中断上，就把这句话作为恢复值交给 review，模型判断 confirm / cancel / modify / other。实测「重疾保额能不能做到50万？预算可以加到一万」被理解为两处修改；「达尔文12号的等待期多久？」被判为 other，方案标为过期，路由按条款问答回答并带引用；之后「还是刚才的条件」能用记住的槽位重新配。
    - 状态与并发（D46）：方案在生成卡片时落库为 pending；只有 pending 能改状态（条件 UPDATE），重复点确认只生效一次；恢复请求必须带上当前待确认的 plan_id，旧卡片上的按钮返回 409。代码审查发现两个坑：恢复接口先 await 再占「会话忙」标记，连点两下会同时恢复同一个中断；删除会话后待确认的方案永远挂着「待确认」。都已修复并补测试。第二轮审查又发现：需求槽位一直留在会话里，「给我老婆也配一份」会悄悄沿用上一个人的预算和排除的产品——方案有了结果就清空槽位（D50）。
    - **原以为**提示词写了「不要写金额、不要说投保」就够了，**结果发现** qwen-plus 仍会写「可以随时确认投保」、编出某款产品「含意外医疗和身故伤残责任」。提示词收紧之后，再在代码里兜底：说明里出现金额（含「三十万」这类中文数字）或「投保」就换成固定模板。
- **R**：真实模型下走通「采集 → 方案卡片 → 打字调整 → 去掉一项 → 转去问条款 → 重新配 → 确认」，浏览器里验证了卡片按钮和「我的方案」页。方案卡片在说完最后一个必填信息后约 6–9 秒出来（其中写说明约 4–6 秒）。服务重启后继续确认：状态在 Postgres checkpointer 里，但未专门测试。
- **可能追问**：
    - 推荐逻辑为什么不用 LLM？→ 推荐结果要能复现、能解释（「预算不够，重疾从 50 万降到 30 万」）；LLM 擅长的是听懂「不要意外险」这种话，交给它抽槽位。代价是规则简单（只比保费，spec Q19），要靠评测发现问题再改。
    - 为什么不在用户问别的问题时保留方案？→ 中断只能有一个；保留的话下一句「确认」到底确认哪个方案就说不清了。过期的方案「还是刚才的条件」一句话就能重配。
- **证据**：`backend/app/agent/advisor.py`、`graph.py` 的 advisor_* 节点；`tests/test_advisor.py`；spec D46–D49。

### 故事 6：长期记忆要用户确认才写入

**一句话**：画像从对话里自动抽取，但只作为「建议」推给前端，用户点确认才写库。

- **S/T**：画像会被带到所有后续会话，还影响报价。一次误抽取（比如把「我妈 58 岁」记成用户本人 58 岁）会长期污染结果。
- **A**：每轮抽取增量 → SSE `profile_suggestion` → 用户确认 → `PUT /profile`。画像是结构化字段而不是自由文本，每个字段记录来源（chat / manual）。
- **取舍**：多一步确认会增加打扰。对保险这种强依赖个人信息、又涉及隐私的场景，可控和知情比无感更重要。
- **M7 实现**：
    - 抽取是和路由**并行**的图分支，只推送建议、失败不影响回答；代码逐项校验模型的 JSON，并和已存画像比较，只推真正新增或变化的内容。实测建议在 2.4–5.4 秒到达，不拖慢回答。
    - 写入分两条路：页面整份保存；对话建议走增量合并接口（成员按 id、保障按「被保险人 + 产品」增改，不删除任何内容），避免「建议生成后用户又在页面改过」被整份覆盖。每个字段记来源（manual / chat / chat_age）。
    - 只知道年龄时出生日期按区间中点估算，并标为估算，页面提示改成准确日期。
- **原以为……结果发现……**：
    1. 原以为难点在「抽错」，结果更隐蔽的是**预填把两个人拼成一个人**。新会话里问「如果我 60 岁再买重疾险会贵很多吗？我朋友今年 45 岁」，顾问的槽位抽取把朋友的 45 岁当成被保险人年龄，预填再用我自己画像里的性别、社保、预算补齐，生成了一个不存在的人的方案。修法：加「为谁配置」槽位（含 other：家人以外的人，不预填）；换被保险人时年龄、性别、社保全部作废；带入了哪些信息由代码写在回复开头，让用户能看到。
    2. 原以为提示词写清楚就够了。「给我老婆配一份，预算三千」：提示词明确写了给家人配置时的预算不算本人预算，qwen-plus 仍把三千建议存成本人预算。改成代码兜底：同一句里在说家人时不建议本人预算。
    3. 「去年 10 月买的」被抽成 2023-10-01：模型按自己的训练时间理解「去年」。提示词里补上今天的日期后正确（2025-10-01）。
- **R**：验收通过——画像齐全时新会话只说「帮我配一份保险」，直接出方案卡片（用了画像预填的 3 次对话，卡片 8.4–13.7 秒，本机 compose），开头写明「已从您的画像带入：32 周岁，女，有社保，年预算 6,000 元」。端到端的抽取准确率待 M8 评测。
- **证据**：`backend/app/agent/profile.py`（build_suggestion、profile_slots）、`advisor.py`（merge_slots、prefill）、`tests/test_profile.py`；spec D51–D53、D55。

### 故事 7：换掉 Milvus，一个库解决一致性

**一句话**：用 PostgreSQL + pgvector 同时承担业务数据、向量和全文检索，父子块在一个事务里写入。

- **S/T**：原项目子块在 Milvus、父块在 PG，双写没有事务，中途失败会出现「子块指向不存在的父块」；部署还要多起 etcd、minio、milvus、attu 四个容器。
- **A**：单库事务写入；向量检索和 `tsvector` 全文检索两路召回，用 RRF 融合后再重排；中文分词放在应用层（jieba），不用自己编译数据库插件。网络调用（解析、向量化）全部放在事务外，事务内先锁文档行再删旧块、写新块，防止同一文档并发入库写出两份。
- **R**：部署从 5 个存储类容器减到 1 个；单事务写入已在 M2 实现，并有测试证明向量化失败时上一版块原样保留。M3 在同一个库里做完了向量 + 全文 + 重排三路对照（结果见故事 10），召回阶段（两路 SQL + 取详情）P50 约 70–90 ms，延迟大头在外部接口：向量化 P50 约 490 ms、重排 P50 约 1.3–1.7 s。
- **踩到的坑**：pgvector 的 HNSW 是「先找近邻再过滤」，默认只找 40 个近邻；按条款过滤后可能只剩几条。用 pgvector 0.8 的 `hnsw.iterative_scan` 解决（过滤后不够会继续往下找），并有测试覆盖条款过滤。
- **可能追问**：数据量大了怎么办？→ 当前是 10 份条款、两千多个块，pgvector 绝对够用；到百万级向量、需要独立扩容时再考虑专用向量库。先说清条件，而不是说谁更好。

### 故事 8：评测集会"自己考自己"

**一句话**：用 LLM 按条款生成的问题，措辞和原文太像，检索指标会偏高；所以另写一组口语化难题，单独报告。

- **S/T**：需要 150+ 条条款问答和 200+ 条路由样本，全部手写不现实。
- **A**：LLM 按父块生成问题 + 人工审核；另手写 ≥30 条口语化、跨章节的难题，指标分开报告；端到端评测用 LLM-as-judge，再人工抽检 20%，报告两者一致率。
- **R**（M3，eval_runs #1–#6）：
    - 生成：10 份条款按章节顺序等距抽 178 个章节，qwen-plus 出题并给出原文依据，脚本校验依据逐字出现在章节里（丢 5 题）；人工审核再删 7 题（目录残留、问公司名之类的元问题），剩 166 题。另手写 34 道口语化 / 同义改写 / 跨章节难题。
    - **量化了「措辞像原文」**：问题与标准章节的最长公共子串，生成集中位数 6 字，难题集 2 字。
    - **差距确实很大**：纯向量 R@5 生成集 0.982、难题集 0.794；MRR 0.891 vs 0.592。只看生成集会以为检索已经「做完了」（混合 + 重排 R@5 = 1.000）。
    - 审核时顺带发现了 2 类结构问题（长病种标题没识别、一份条款的目录没删干净），评测集也是数据质量的检查工具。
- **可能追问**：LLM-as-judge 可信吗？→ 所以要报告它和人工判断的一致率，而不是直接拿来当真值。
- **可能追问**：34 题的难题集够吗？→ 不够做精细调参（一题就是 3 个百分点），所以只用它看方向、不用它挑最优参数；调参结论要在两个集上方向一致才采用（见故事 10）。
- **证据**：`data/eval/`、`backend/app/eval/`、报告 `eval/reports/retrieval-document-20261121-185832.md`。

### 故事 9：用规则重建条款结构，规则从真实解析结果里一条条补出来

**一句话**：不让 LLM 改写条款，而是用编号规则重建章节层级；第一版规则在真实数据上暴露了 8 类问题，逐个修复并加回归测试后，福有余条款的父块从 10 个恢复到 25 个，最长子块从 7754 字降到 1130 字。

- **S**：M2 入库，10 份条款经 MinerU 解析成 Markdown。MinerU 给的 `#` 级别不可靠，原项目的做法是让 LLM 整篇改写。
- **T**：在不改动条款原文的前提下，得到正确的章节路径（用于引用出处和父块上下文）。
- **A**：
    - 只做删行、拆行、接行、改标题标记，正文一个字不改；8 类编号（第X部分 / 第X条 / （一） / 一、 / （1） / 1. / 1.1 / 1.1.1）按首次出现顺序分配层级，中文和数字两套编号体系都适用。
    - 第一版规则是用 pypdf 文本设计的。拿到 MinerU 真实输出后逐份检查，发现：漏了「一、」编号；MinerU 会把整句话标成标题；同级的（一）（二）被错误嵌套；PDF 换行把列表项截成「带编号的半句话」被误判成标题；三栏目录挤成一行；双栏排版把「标题 + 正文」合成一行（星辰守护一份就有 93 处）；附表疾病定义变成长达 7754 字的表格。
    - 对应规则：带层级的标题栈、数字编号前缀一致性（9.4 只能挂在 9. 下）、接断行、删目录块、拆双栏行、长表格按行拆并保留表头。每条规则一个回归测试，测试用例直接取自真实输出。
    - 每一步的删除/合并/拆分次数写进文档统计，在管理后台展示，新条款结构异常一眼可见。
- **R**：10 份条款全部入库，共 974 个父块、1423 个子块；福有余父块 10 → 25；最长子块 7754 → 1130 字。检索效果待 M3 评测。
- **代码审查又抓到的问题**：删目录块的规则只比较「第 1 章编号是否出现第二次」，而 `1.` 的正则会匹配到 `1.1`——目录项早被逐行删掉时，它把真正的第 1 章标题和一段定义正文（「‘您’指投保人」）一起删了，3 份条款受影响，测试和统计都没发现。修复：编号后不能紧跟数字，且两次出现的**标题文字必须相同**；目录块内的完整句子保留。教训：**删除型规则要专门验证「删掉了什么」**，现在改规则后会在全部真实条款上列出被删的行逐条核对。同一轮还发现「标题含逗号就当正文」误伤了 2 个真实标题（改为看括号是否配对）、「第 1章」这种带空格的阿拉伯数字章号没识别。
- **后续（M4 之后，Q12/Q13）**：引用在对话里对用户可见后，章节名错误不再只是统计问题，于是单独做了一轮结构修复：
    - 计划修 2 个问题（附表里超过 20 字的病种名被当正文；众安释义条目层级挂错），在全部条款上对比修复前后的章节时又挖出 4 个：信美的编号末级有 3 位（8.1.100–8.1.117）、有 4 级编号（1.5.1.12），都识别不出，导致「1.5.1.13」一节有 6241 字；达尔文有只剩编号的标题「## 2.3.3.4」；两份条款的「条款目录」前有 PDF 图标字体字符，目录没删掉。
    - **原以为……结果发现……**：原以为重新入库后只要更新「路径不存在了」的评测题。结果发现有的题路径仍然有效，但答案已经搬到新识别出的章节里了（gen-100/115）——只校验路径，指标会悄悄失真。于是评测脚本加了一道检查：生成题的原文依据必须仍在标准章节里（D40），并按依据重新标注了 16 题。
    - 结果：父块 974 → 985；难题集 R@5 0.912 → 0.941、MRR 0.818 → 0.828（eval_runs #70，评测集已重新标注，仅供参考），生成集持平。每条新规则一个取自真实输出的回归测试，并确认去掉规则后测试会失败。
- **已知局限**：双栏排版的左栏标题会被截断（「1.2 合同成立与生」），只影响引用展示的标题；MinerU 偶尔丢失或错放病种标题（gen-082/122），规则修不了。
- **可能追问**：规则怎么保证对新条款也有效？→ 不能保证，所以把结构统计做成可观测的（超大章节、超长标题、修正父级次数），新条款入库后先看统计。为什么不用 LLM？→ 长文会被截断、无法保证不改原文、每次重跑都有成本，而规则可解释、可测试、零成本。
- **证据**：commit `c8c9edf`；`backend/app/rag/structure.py`、`backend/tests/test_rag_structure.py`。

### 故事 10：原以为混合检索一定更好，难题集上它反而更差

**一句话**：加上全文召回后，口语化难题的 R@5 从 0.794 掉到 0.676，因为口语里的「住院」「钱」「报」在条款里到处都是；真正起作用的是重排，而且换一个重排模型（gte-rerank-v2 → qwen3-rerank）难题集 R@5 就从 0.79 到 0.91——调参不如换对组件，而这只有难题集看得出来。

- **S**：M3 做混合检索（pgvector 向量 + PostgreSQL 全文，RRF 融合，再用 gte-rerank-v2 重排），在生成集 166 题 + 手写难题 34 题上做三组对照。
- **T**：用数据决定线上用哪种配置，而不是默认「混合 + 重排」就一定最好。
- **A**：
    - 先把全文召回做对：PostgreSQL 的 `ts_rank` 不看词的稀有程度，每个子块又都带条款名前缀，几乎所有块同分；改成按 BM25 的 IDF 给命中词加权（SQL 里逐词求和），并忽略出现在一半以上子块里的词。
    - 三组对照的结果：

        | 评测集 | 配置 | R@1 | R@5 | MRR@10 | P50 |
        |---|---|---|---|---|---|
        | 生成集 | 纯向量 / 混合 / 混合+重排 | .819 / .843 / .970 | .982 / .994 / 1.000 | .891 / .907 / .984 | 569 / 580 / 2310 ms |
        | 难题集 | 纯向量 / 混合 / 混合+重排 | .471 / .235 / .500 | .794 / .676 / .794 | .592 / .439 / .619 | 547 / 548 / 2047 ms |

    - **原以为……结果发现……**：原以为混合检索至少不会比纯向量差。结果在难题集上 R@1 从 0.47 掉到 0.24。看错题：「生病住院，自己要先掏多少钱保险才开始报？」，全文一路把十几个「住院医疗费用」章节排在前面，因为它们字面上命中「住院」「费用」「保险」，而真正的答案在「免赔额」一节，问题里一个字都没出现。RRF 给两路同样的权重，噪声一路就把好结果挤下去了。
    - 试了降低全文权重（1.0 → 0.5 → 0.3）：不重排时难题集 MRR 0.44 → 0.47 → 0.51，仍不如纯向量的 0.59；**加上重排后，三个权重的结果几乎一样**（两个集上差异都不超过 1 题：重排对前 30 个候选重新打分，候选集合基本没变）。所以线上默认保持「混合 + 重排」、权重不动，而没有为了 34 道题去调一个最优权重。
    - 最后对比了两个重排模型（其他不变）：

        | 难题集 | R@1 | R@5 | MRR | 总 P50 |
        |---|---|---|---|---|
        | gte-rerank-v2 | .500 | .794 | .619 | 2047 ms |
        | qwen3-rerank | .735 | .912 | .818 | 2391 ms |

      生成集上两者几乎一样（R@1 .970 vs .964），**只有难题集能区分它们**——这也是故事 8 里坚持单独做难题集的价值。原以为 qwen3-rerank 更快（单次试调 0.5 秒 vs 1.6 秒），批量跑下来 P50 相近，单次测量不可信。
    - 剩下 3 道没进前 5 的难题都是口语和条款术语之间的鸿沟：「之前就有的病」↔既往症、「刚买完就查出来」↔等待期、「突发心梗走了」↔疾病/猝死免责。这是查询改写要解决的问题，留给 M4（路由后先把问题改写成条款用语）。
- **R**：线上默认「混合 + 重排（qwen3-rerank）」：相对纯向量，生成集 R@1 0.82 → 0.96，难题集 R@5 0.79 → 0.91、MRR 0.59 → 0.82；代价是 P50 延迟多约 1.7 秒（重排接口）。所有数字来自 eval_runs #1–#22，管理后台「评测记录」页可查。
- **可能追问**：34 题上的差距可信吗？→ R@5 多对 4 题、R@1 多对 8 题，方向和幅度都远超 1 题的噪声，且生成集上没有变差，所以采纳；但全文权重那种 ≤1 题的差异就不采纳。延迟代价 M4 看端到端再评估（可减少候选数）。
- **可能追问**：为什么不直接用 Elasticsearch 的 BM25？→ 数据量只有 1400 个子块，在 PG 里用 IDF 加权已经够用，而且能和向量检索在一条 SQL 链路里按条款过滤；全文一路的问题不在打分公式，在于口语词本身没有区分度。
- **证据**：`backend/app/rag/retriever.py`；`eval/README.md`；eval_runs #1–#22。

### 故事 11：查询改写的提升，是我把评测集写进了提示词

**一句话**：给检索加了「口语→条款术语」的查询改写，难题集 R@5 从 0.912 涨到 0.971；后来发现提示词里的示例就是照着难题集错题写的。去掉这些示例重测，改写在两个集上都比不改写差，于是线上不换术语，只用改写补全指代。

- **S**：M4 做条款问答。M3 留下的问题（Q14）是口语和术语的鸿沟：「自己先掏多少钱」对应免赔额，难题集错题大多是这类。
- **T**：试查询改写能不能补上这个鸿沟，用评测说话。
- **A**：
    - 评测脚本加了 `--rewrite`，用线上同一个改写函数；又加了 `--keep-original`（改写结果和原问题一起召回）。
    - 第一版结果很好看：难题集 R@5 0.912 → 0.971、MRR 0.818 → 0.878（#45）。
    - **原以为……结果发现……**：原以为是改写起作用了。整理结果时回头看提示词，里面的「口语→术语」示例：自己先掏的钱→免赔额、买之前就有的病→既往症、刚买完多久能赔→等待期、取钱→减保、用保单借钱→保单贷款……全是我分析难题集错题时看到的。这是数据泄漏：评测集的答案写进了模型输入。
    - 去掉这些示例，只描述原则重测：难题集 R@5 0.941、MRR 0.785，生成集 MRR 0.980 → 0.962，都不如不改写（#46/#47 对 #21/#22）。
    - 看具体例子，改写把「哪些人住院时可以报销陪护人员的加床费？」变成了「住院医疗费用 加床费 陪护人员 保险责任 责任免除」：丢掉了和条款原文一致的措辞，又加了噪声关键词。
    - 决策：线上改写只补全指代（「那生孩子呢」→「生孩子住院能报吗」），不换术语；第一句没有上文就不改写，还省一次 LLM 调用；改写结果和原问题一起召回。
- **R**：评测集上的独立问题，线上检索等于基线（混合 + qwen3-rerank：难题集 R@5 0.912、MRR 0.818）；口语鸿沟仍是已知局限（Q14）。所有数字来自 eval_runs #21–#49，见 `eval/README.md`。
- **教训**：评测集只能用来评估，看过的失败案例不能回流到提示词或规则里；需要调参时要留出单独的开发集。这条已写进 CLAUDE.md。
- **可能追问**：那 M3 里根据难题集选 qwen3-rerank 算不算泄漏？→ 那是在两个现成模型之间选一个，没有把题目内容写进系统；而且生成集上两者持平，结论不依赖难题集的具体题目。但严格来说也该有开发集，M8 扩充评测集时会拆出来。
- **证据**：`backend/app/agent/prompts.py` 的 REWRITE；`eval/README.md`「查询改写」一节；eval_runs #39–#49。

### 故事 12：理赔咨询——「能不能赔」的答案不在用户问的地方

**一句话**：理赔问题只检索问题本身时，等待期和责任免除章节进不了上下文；改成问题、责任免除、等待期、理赔材料四路并行检索；模型推算日期会算错，改由代码算好「已生效 N 天」再交给它比较。

- **S**：M7 做理赔咨询（D18）：只查用户名下保单的条款，输出初步判断、依据条款、材料、流程。
- **T**：用户问「我上周阑尾炎住院做了手术，能赔吗」，能不能赔取决于等待期、责任免除，用户不会这么问（Q14 的同一个问题）。
- **A**：
    - 保单来源由代码决定：本轮提到的产品 > 画像里这个人名下登记的库内产品；都没有就追问并建议去画像登记；只有库外产品就给固定的通用指引，不调模型。追问换了人（「那我老婆住院呢」）时，不能沿用上一轮另一个人的保单（代码审查发现，已加回归测试）。
    - **原以为……结果发现……**：第一版三路检索（问题、问题 + 责任免除、理赔材料），真实测试时模型回答「条款中无等待期天数规定」——2.5 等待期章节根本没被检索到。加第四路「等待期」后进了上下文。
    - 接着发现模型自己推算「2025-10-01 起 90 天」：两次分别算成 2026-01-08 和 2026-01-01（正确是 2025-12-29）。和报价一样（故事 4），日期计算也不交给模型：代码算好「到今天已生效 417 天」写进提示词，模型只做比较。
    - 「最终以保险公司审核为准」由代码保证：模型没写就补上。
- **R**：真实条款（星相守2号）上回答引用了一般住院医疗、责任免除、等待期、保险金申请四个章节，判断「已生效 417 天，远超 90 天等待期」。延迟偏高：首 token 12–15 秒、完整 20–23 秒（3 次，Q22）。回答质量待 M8 端到端评测。
- **可能追问**：四路检索不会太慢吗？→ 四路并行，耗时约等于一路；真正的瓶颈是路由和理赔抽取两次串行 LLM 调用，可以合并（Q22）。
- **证据**：`backend/app/agent/graph.py` 的 claim_prepare / claim_answer；spec D54、Q22。

### 故事 13：评测体系——开发集和测试集分开，裁判要先量一致率

**一句话**：路由评测按 M4 的泄漏教训一开始就分开发集和测试集（测试集 0.956，只报告不调）；端到端用另一个更强的模型当裁判，但裁判的分数在测出和人工的一致率之前只当参考；接上 Langfuse 后，第一个 trace 就看出 token 用量全是 0。

- **S**：M8 要给路由、端到端各出一套可复现的指标，并接上 LLM 可观测性。
- **A**：
    - **评测和线上共用函数**：把路由（寒暄规则 + 模型 + 产品 id 校验 + 追问沿用产品）和「检索 + 带引用生成」从图节点里提出来，节点和评测都调它们，评测数字才代表线上。
    - **路由集**：手写 203 题测试集（55 题多轮：追问省略主语、只回产品名、从顾问跳到问条款、「我真的已经住院了」这种从条款问答转理赔）+ 51 题开发集，两份不重题。调提示词只看开发集（98.0%，#142）。测试集 95.6%（#143）的 9 道错题里，有 2 道本身有歧义（「孩子在幼儿园摔掉门牙报不报」可能已经出险），也不在看到结果后改标签。
    - **端到端**：不手写参考答案，裁判对照标准章节原文打分；裁判用 qwen-max，回答用 qwen-plus，避免自评。另加 12 道「条款里没有答案」的题测拒答，其中一道是陷阱：「保费能用信用卡分 12 期吗」——条款里有「分期支付保险费」（指按年交），模型容易混为一谈。
    - **原以为……结果发现……**：原以为裁判分数可以直接用。看失败案例发现 16 个 partial 里有几个是裁判只看到标准章节，把回答里来自其他章节的正确信息当成「额外信息」扣分——这正是要人工抽检、报告一致率的原因。抽 20%（17 题）导出 CSV，人工标注后 `agreement` 命令算一致率和 Cohen's kappa，写回同一条评测记录。
    - **原以为……结果发现……**：接上 Langfuse 后看第一个对话 trace，节点耗时都有，token 用量全是 0；评测里裁判的调用却有用量。原因是对话图用 messages 流模式，图里每一次模型调用（包括路由的 JSON 调用）都会走流式，而兼容接口流式时默认不返回用量。开 `stream_usage` 后才能看到每轮约 3.2–3.8k token：路由 620、画像抽取 710、回答 1.8–2.5k（输入）。
    - **原以为……结果发现……**：端到端第一次跑到一半连接被断，整次作废（事后知道是阿里云账号欠费）。加了每题重试；重试后仍失败就让整次失败、不写记录——只写成功的题会留下题数不对、悄悄偏高的指标。
    - **原以为……结果发现……**：人工标完 17 题，正确性一致率 76%，看着还行，Cohen's kappa 却只有 0.15。原因是绝大多数答案都是 correct，两个人闭着眼都判 correct 也能高度一致；扣掉偶然一致后，裁判和人工几乎没有「判断上的一致」。再看分歧方向：4 处里 3 处是裁判更严——答对了但多说了几句（「年满 105 周岁前可重新投保」「顺带提了保单贷款」），裁判判 partial；引用上则相反，2 处分歧都是裁判更松。所以 0.878 只能当正确性的下限，不能当真值。
    - **改裁判也要分开发集和测试集**：17 道人工标注拿来调裁判（开发集），回答不重新生成、只换裁判重判（`rejudge`），新裁判的一致率在另抽的 17 题上盲标报告。v2 给裁判全部段落、要求引用逐字摘录由代码核对，结果从偏严变成偏松（17 题全判 correct，kappa 0）、引用核对又被格式卡住（JSON 里的字面换行、上标、半角标点）；v3 修了格式，但「健康管理系数仅影响一般医疗」这种原文没说的限定说法，提示词专门强调了，qwen-max 仍判 correct。教训：开发集里只有 1 道错题，一致率根本测不出裁判能不能区分对错——要评估裁判，先得有足够多的错误样本。
    - **测试集上的结论**：另抽 17 题盲标（人工判 3 道 partial），v3 正确性一致 0.882、kappa 0.45，好于 v1 的 0.765、0.19——v1 的两次「答对但多说判 partial」没了；但 3 道 partial 两版都只抓到 1 道，裁判仍偏松。引用反过来，v1 的整体判断更接近人工（0.941 vs 0.765）：要求摘录核对让裁判在「拿不准」时更容易判无依据，还有一次是裁判输出里夹了引号导致核对失败——这个是在测试集上发现的，记下来留给下一批新样本验证，不在同一批题上改了重测。最后报数以人工抽检为准：30 道有答案题人工正确性 0.917。
- **R**：路由测试集准确率 0.956、宏 F1 0.952、多轮 0.964、产品识别 0.991（#143）；端到端无答案题拒答率 1.000、误拒率 0（#147）；正确性以人工抽检为准 **0.917**（30 道有答案题），裁判 v3 打 0.966（#158，测试集上与人工一致 0.882、kappa 0.45，偏松）、v1 打 0.878（一致 0.765、kappa 0.19，偏严）。trace 拆分：一轮条款问答首 token 7.6–9.8 秒，回答节点 7.7–10.0 秒是大头，画像抽取与路由并行不在关键路径上。
- **可能追问**：kappa 0.15 这么低，这个评测还有用吗？→ 有用的部分是方向和失败案例：拒答判断完全一致，正确性的分歧集中在「答对了但多说」这一类，说明裁判的标准比人严。它适合做回归对比（同一个裁判前后两版比），不适合报绝对数字；要报绝对数字就得改裁判（给它全部引用段落）再抽检。
- **可能追问**：为什么端到端不评顾问和理赔？→ 顾问的数字来自报价引擎（已有 107 个抽样点单测），推荐规则的问题（Q19、Q21）要先补带标准方案的题；理赔还没有带标准结论的题集，下一步补。
- **证据**：`backend/app/eval/`（routing.py、e2e.py、retry.py）、`data/eval/routing_*.jsonl`、`e2e_clause.jsonl`、`eval/reports/`、`backend/app/infra/tracing.py`；spec D56–D60、Q23、Q24。

## 简历要点

写简历时从这里挑 3–5 条。每个数字都能在 `eval_runs` 或单测里找到出处（括号里是运行编号）；裁判分数注明裁判模型和一致率。

**一句话介绍**：独立设计并实现的保险顾问 Agent（FastAPI + LangGraph + PostgreSQL/pgvector + React），覆盖条款问答、方案推荐、精确报价、理赔咨询，配套检索 / 路由 / 端到端 / 报价四类评测。

- **Agent 架构**：用 LangGraph「路由 + 子图」组织 4 条业务线，LLM 只做意图识别与表达，产品 id、检索参数、保费、日期计算全部由代码决定；方案确认用 `interrupt` + Postgres checkpointer，支持点按钮或直接打字调整。路由测试集（203 题，含 55 道多轮）准确率 95.6%（#143）。
- **RAG**：规则化重建条款结构（不经 LLM 改写原文）、父子块切分、向量 + BM25 加权全文混合召回、RRF 融合、qwen3-rerank 重排；手写口语难题集 R@5 从纯向量的 0.794 提到 0.941、MRR 0.605 → 0.828（#68 / #70）。对照实验发现不加重排时混合检索在口语题上反而比纯向量差（R@5 0.647），据此确定线上配置。
- **防幻觉**：回答引用由代码解析、只保留本轮检索到的编号；端到端 86 题中 12 道「条款里没有答案」的题拒答率 100%、编造率 0，有答案题误拒率 0（#147）；人工抽检 30 道有答案题正确性 0.917。
- **报价引擎**：把 10 份格式各异的费率表 PDF（5 种版式，6.4 万个单元格）按单元格位置提取成 JSON，加业务规律校验（交费期 / 年龄单调性等）挡住空白格导致的错列；对照 PDF 页面图像人工读出的 107 个抽样点 100% 一致，每笔报价可追溯到「第几页哪一格」。
- **评测方法**：发现并修正了一次评测集泄漏（改写提示词示例取自难题集错题，R@5 虚高 0.971 → 实际 0.912），此后路由与 LLM 裁判都分开发集 / 测试集；LLM 裁判（qwen-max）在盲标测试集上与人工一致 0.882（Cohen's kappa 0.45），据此决定报数以人工抽检为准。
- **工程化**：全链路 async，Docker Compose 一键部署，GitHub Actions 跑 ruff / mypy / alembic check / 406 个后端单测与前端 lint、类型检查、Vitest；Langfuse 自托管 trace 定位到流式模式下 token 用量丢失并修复。

**面试时别说过头的地方**：
- 端到端只评了条款问答；顾问推荐规则很简单（取最便宜的可投保产品），没有带标准方案的评测题。
- 裁判分数（v3 0.966）偏高，引用忠实度的裁判数字也只是参考；能站住的是人工抽检的 0.917（样本 30 题，置信区间宽）。
- 首 token 7–10 秒（理赔 12–15 秒），没有做延迟优化。
- 数据规模小：10 份条款、985 个章节块，没有压测。
